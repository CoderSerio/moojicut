# UI：记录组件体验与声明式 API 方向，随产品迭代提取

> 已发布：[GitHub Issue #1](https://github.com/CoderSerio/mooncap/issues/1)。本文保留可在仓库内修改的需求正文。

## 背景

用户希望有一套更好理解、更好看、更容易使用的 MoonBit UI 能力。当前先提交 Mooncap 的 [交互初稿](../interaction-design.md) 和基础框架，后续由用户直接修改交互方案；UI 库的想法继续保留在本 Issue 中。

现有 HTML、JavaScript 和手写 CSS 大窗口是开发工作台，用于验证采集、编辑与导出，不是正式产品首页。正式目标是菜单栏/托盘待命、截图桌面就地完成、录屏结束后才打开编辑窗。桌面覆盖层尚未实现，不能以工作台页面代替这一产品交互。

## 已明确的痛点

以下是用户的使用感受和期待，不是对所有现有库的客观评测结论。

1. **组件难找**：缺少清楚的组件目录，不容易知道有什么组件、应该从哪里开始。
2. **API 难理解**：接口说明不足，组件的属性、事件和状态关系不直观。
3. **示例不完整**：缺少可直接运行、可修改的示例，难以从文档走到实际使用。
4. **文档体验差**：查找组件、了解 API、运行示例的路径不连贯。
5. **视觉质量不理想**：默认外观、间距、状态反馈和整体一致性未达到用户期望。
6. **不喜欢现有客户端式 API**：更希望用接近 TSX 的声明式方式描述界面，组件结构应清楚可读。

“接近 TSX”在这里表达的是编写和阅读体验的偏好，尚未决定新增语法、预处理器或编译器插件。

## 当前决定

- 先保留基础框架与明确的交互草案，后续沿实际产品流程迭代。
- 界面暂用手写样式，不把开发工作台固化为产品主窗口。
- 用户希望部分操作换为图标：矩形、箭头、文字、遮挡、撤销和裁切等工具可用纯图标；开始、停止、导出和确认保留文字。
- 图标必须同时提供 tooltip、可访问名称、键盘焦点和适用快捷键，不以隐藏文字牺牲操作含义。
- 从真实重复中提取组件，不为可能出现的需求预先设计抽象。
- 本阶段不启动跨平台 UI 框架，不重写现有语言工具链。
- 若后续值得建设通用库，组件应独立于截图、录屏等产品专用状态；产品只是验证场景。

## 后续提取时需要满足的要求

- 有可浏览的组件目录，能够快速找到基本控件及其用途。
- 每个公开组件都有属性、事件、状态和最小使用示例。
- 示例能够运行，并展示正常、禁用、加载、错误等适用状态。
- 组合方式清楚，能够从声明式结构中看懂界面层级。
- 默认视觉表现达到实际产品可用水平，允许统一调整样式。
- 键盘操作、焦点、文本输入和可访问性是组件行为的一部分。
- 用 Mooncap 的桌面工具条、录屏准备和紧凑编辑窗验证 API，不只验证工作台或孤立的组件展示页。

## 尚未决定的问题

- 提取出的代码是否适合作为独立库发布。
- 声明式写法使用 MoonBit 现有语法、组合函数，还是额外工具。
- 是否需要渲染器抽象，以及未来是否支持其他宿主。
- 哪些控件已有足够重复，值得从产品中抽出。

这些问题待产品使用暴露出具体需求后再决策，不作为当前截图录屏功能的前置条件。

## 进入实现前的检查

- [ ] 找到实际重复的组件或行为，并列出至少两个使用位置。
- [ ] 用真实页面比较提取前后的写法与维护成本。
- [ ] 明确通用组件与产品专用逻辑的边界。
- [ ] 确定首批组件及其可运行文档范围。
- [ ] 再决定是否创建独立库或进一步讨论框架设计。
